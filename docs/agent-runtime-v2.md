# Agent Runtime v2

Agent Runtime v2 是企微群监听回复的下一代执行底座。它借鉴 pi 的核心设计取向：让模型在受控环境中持续观察工具结果、决定下一步，并把执行过程变成可恢复、可审计的状态，而不是把 Agent 简化成一次 JSON 规划。该实现不依赖 pi 运行时，也不会放宽本项目既有的证据复核、人工抢答和发送门禁。

## 执行模型

一次模型决策以及该决策产生的零到多个工具调用记为一轮。MCP 工具结果写回模型上下文后，模型可以继续补查、改写查询条件、切换工具或停止。监听器可分别配置：

- 最大查询轮数：2–200，默认 6。
- 最大工具调用尝试：1–200；失败、非法参数和重复尝试均计入预算。
- 单个问题 MCP 总超时：覆盖首轮必查、模型决策和所有 MCP 调用。
- 首轮必查：对指定工具保存 Schema 绑定的固定 JSON 参数，并在第一次自由决策前按配置顺序执行。

达到轮次、调用或超时边界后，运行时停止继续访问 MCP。已有证据时只允许基于已收集证据生成和复核答案；没有证据时不会编造回答。模型中间文本永远不会直接成为企微发送内容。

## 工具安全模型

Agent v2 根据 MCP annotations 和本机确认记录将工具分为：

| 分类 | Agent v2 行为 | 人工覆盖 |
| --- | --- | --- |
| `read_only` | 可在精确授权后调用 | 不需要 |
| `unknown` | 默认阻止 | 可针对当前 Schema Hash 确认为只读 |
| `write` | 不向模型暴露 | 禁止 |
| `destructive` | 不向模型暴露 | 禁止 |

人工只读确认同时绑定服务、工具名和 Schema SHA-256。工具结构变化后确认自动失效，必须重新测试和确认。MCP annotations 只是安全提示，不替代权限边界；显式写入或破坏性声明始终优先于旧确认。

监听器保存的授权仍精确绑定服务、工具名和 Schema Hash。运行前再次校验目录、启用状态和安全分类，避免配置变化后扩大权限。

## 上下文与证据

- 当估算上下文达到模型配置预算的约 80% 时，运行时压缩较早的已完成轮次。
- 压缩摘要只来自已经取得的工具证据，并保留最近一组完整的模型/工具相邻关系。
- 单条工具结果提供给模型的视图最多 12,000 字符，避免超长返回挤占决策空间。
- 审计证据仍保存完整的脱敏结果；模型视图截断不等于删除原始证据。
- 空结果允许 Agent 继续改写条件，但不计为有效业务证据。
- 图片和文件只作为问题上下文，不能绕过 MCP/Dify 的证据门禁。

## 检查点与恢复

每个工作项保存 Runtime、回答引擎、当前阶段、工作 generation、停止原因、Usage、provider audit 和持久化时间线。应用重启后的规则是：

- 收集补充、等待图片缓存、等待群友和排队检索等确定性阶段可以继续。
- MCP 检索仅在本轮所有工具均确认为只读时重新排队；重新执行会创建新的 generation，旧时间线保留。
- Dify 请求以及任何副作用不确定的工具调用不会自动重放，避免重复计费或重复写入。
- 在发送附近中断的工作项不会假定发送成功，而是进入人工可核对状态。
- 人工重试会清理旧的临时执行状态、增加 generation，并立即记录 `manual_retry_scheduled`。

恢复是 at-least-once 的只读重查，不是对外部系统的 exactly-once 保证。任何发送状态不确定的消息都应先在企微群中核对。

## 时间线、日志与诊断

轻量时间线始终开启，默认只保存阶段、耗时、轮次、工具名称、计数、停止原因和 Token Usage 等元数据。工作详情按角色折叠显示，并支持按 Runtime、引擎、阶段、停止原因和恢复状态筛选。

详细日志默认关闭。排查时可在“设置 → 诊断与日志”开启；只有之后新开始的工作项才记录模型决策、工具参数/返回、证据判断和复核明细。页面同时提供：

- 模型能力检测：结构化输出、原生 Tool Calling、图片输入和上下文读取。
- 日志目录、文件数量、占用和保留状态。
- 按工作项导出诊断包及人工重试。
- 带二次确认的详细日志清理。

日志会遮蔽 API Key、Bearer Token、Authorization、Webhook、MCP Headers/Env 和已登记密钥，但问题文本、查询参数、工具结果与回答草稿本身仍可能属于敏感业务数据。诊断包只应在受控范围内流转。

## 回答引擎边界

`MCP + 提示词` 使用 Agent v2 的多轮工具循环。`Dify` 继续使用已发布 Chatflow：附件按消息顺序上传，随后解析流式回答；它不复用 MCP 工具循环，也不会在失败时回退 MCP。两种引擎之后都经过相同的空证据门禁、答案压缩、独立复核、人工抢答检查和 webhook 发送门禁。

旧监听器默认保持 Legacy，便于灰度迁移；新建监听器默认 Agent v2。运行过程中不会因为模型不支持 Tool Calling、工具错误或上下文过长而静默回退 Legacy。

## UI 操作建议

1. 在“设置 → 模型与 OCR”检测 Agent v2 模型能力。
2. 在“MCP 服务”重新测试服务，查看每个工具的安全分类；仅对确知无副作用的未知工具做只读确认。
3. 在监听器中选择 Agent v2，配置精确工具、首轮必查和轮次/调用预算。
4. 先使用“审核后发送”观察时间线和回答质量，再决定是否启用自动发送。
5. 检索异常时先导出单个工作项诊断；只有确需完整参数和结果时才临时开启详细日志。

高轮次并不等于更高质量。建议先通过首轮必查、工具描述和系统提示词改善查询路径，再提高轮次；轮次、调用量、模型费用和总耗时会同时增长，而且 MCP 总超时仍可能先终止任务。

## 开发与发布约束

开发机只运行 Python、前端和 Rust 源码级检查，以及 Vite renderer 构建。禁止在本机运行 PyInstaller、Tauri 打包、EXE/MSI/NSIS 构建或安装包自检。

Windows sidecar、签名、安装包和安装级冒烟验证只在 GitHub Actions Windows Runner 执行。正式版本需要同步更新 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 和 `src-tauri/Cargo.lock`，提交到 `main` 后推送匹配的 `vX.Y.Z` 标签。
