# Agent Runtime v2

Agent Runtime v2 是企微群监听回复的下一代执行底座。它借鉴 pi 的核心设计取向：让模型在受控环境中持续观察工具结果、决定下一步，并把执行过程变成可恢复、可审计的状态，而不是把 Agent 简化成一次 JSON 规划。该实现不依赖 pi 运行时，也不会放宽本项目既有的证据复核、人工抢答和发送门禁。

> v4.2 起群监听只支持 Agent V2。Legacy 运行时已删除；旧监听器在保存时自动归一为 v2，历史工作项仍可查看。

## 执行模型

一次模型决策以及该决策产生的零到多个工具调用记为一轮。MCP 工具结果写回模型上下文后，模型可以继续补查、改写查询条件、切换工具或停止。监听器可分别配置：

- 最大查询轮数：2–200，默认 6。
- 最大工具调用尝试：1–200；失败、非法参数和重复尝试均计入预算。
- 单个问题 MCP 总超时：覆盖模型决策和所有 MCP 调用。
- 并发与等待：同一发送者始终串行；群友回答等待、连续补充合并、问题检索并发数可配。

达到轮次、调用或超时边界后，运行时停止继续访问 MCP。已有证据时只允许基于已收集证据生成和复核答案；没有证据时不会编造回答。模型中间文本永远不会直接成为企微发送内容。

## 工具安全模型

Agent v2 根据 MCP annotations 在运行时动态构建工具集合，**只读工具自动可用，写/破坏性/未声明工具不会进入模型可用列表**：

| 分类 | Agent v2 行为 | 人工覆盖 |
| --- | --- | --- |
| `read_only` | 自动提供给模型，可多轮调用 | 不需要 |
| `unknown` | 不向模型暴露，不可调用 | 不提供人工放行 |
| `write` | 不向模型暴露，不可调用 | 禁止 |
| `destructive` | 不向模型暴露，不可调用 | 禁止 |

工具集合来自所有已启用且连接有效的 MCP 服务。MCP 服务连接或目录变化后，运行时重新计算工具集合；正在执行的 MCP 工作会被保守关闭，避免用旧目录继续访问。Schema SHA-256 仍会记录在审计快照中，但不再要求用户逐项授权或重新确认。

群监听编辑器不再有“工具策略 / 精确授权”步骤；选择 MCP 引擎后，后端自动暴露只读工具。没有可用的只读工具时，监听器健康状态会给出可读提示。

## 上下文与证据

- 当估算上下文达到模型配置预算的约 80% 时，运行时压缩较早的已完成轮次。
- 压缩摘要只来自已经取得的工具证据，并保留最近一组完整的模型/工具相邻关系。
- 单条工具结果提供给模型的视图最多 12,000 字符，避免超长返回挤占决策空间。
- 审计证据仍保存完整的脱敏结果；模型视图截断不等于删除原始证据。
- 空结果允许 Agent 继续改写条件，但不计为有效业务证据。
- 图片和文件只作为问题上下文，不能绕过 MCP/Dify 的证据门禁。

## 检查点与恢复

每个工作项保存 Runtime、回答引擎、当前阶段、工作 generation、停止原因、Usage、provider audit 和持久化时间线。应用重启后的规则是：

- 收集补充、等待图片缓存、等待群友和排队检索等确定性阶段可以继续。
- MCP 检索只会在工具集合仍全部为只读时重新排队；重新执行会创建新的 generation，旧时间线保留。
- Dify 请求以及任何副作用不确定的工具调用不会自动重放，避免重复计费或重复写入。
- 在发送附近中断的工作项不会假定发送成功，而是进入人工可核对状态。
- 人工重试会清理旧的临时执行状态、增加 generation，并立即记录 `manual_retry_scheduled`。

恢复是 at-least-once 的只读重查，不是对外部系统的 exactly-once 保证。任何发送状态不确定的消息都应先在企微群中核对。

## 时间线、日志与诊断

轻量时间线始终开启，默认只保存阶段、耗时、轮次、工具名称、计数、停止原因和 Token Usage 等元数据。工作详情按角色折叠显示，并支持按引擎、阶段、停止原因和恢复状态筛选。

详细日志默认关闭。排查时可在“设置 → 诊断与日志”开启；只有之后新开始的工作项才记录模型决策、工具参数/返回、证据判断和复核明细。页面同时提供：

- 模型能力检测：结构化输出、原生 Tool Calling、图片输入和上下文读取。
- 日志目录、文件数量、占用和保留状态。
- 按工作项导出诊断包及人工重试。
- 带二次确认的详细日志清理。

日志会遮蔽 API Key、Bearer Token、Authorization、Webhook、MCP Headers/Env 和已登记密钥，但问题文本、查询参数、工具结果与回答草稿本身仍可能属于敏感业务数据。诊断包只应在受控范围内流转。

## 回答引擎边界

`MCP + 提示词` 使用 Agent v2 的多轮工具循环。`Dify` 继续使用已发布 Chatflow：附件按消息顺序上传，随后解析流式回答；它不复用 MCP 工具循环，也不会在失败时回退 MCP。两种引擎之后都经过相同的空证据门禁、答案压缩、独立复核、人工抢答检查和 webhook 发送门禁。

运行时不会因为模型不支持 Tool Calling、工具错误或上下文过长而静默回退到已删除的 Legacy 运行时；无法继续时会给出明确的停止原因。

## UI 操作建议

1. 在“设置 → 常用”检测模型能力，确认模型支持 Tool Calling 与结构化输出。
2. 在“MCP 服务”登记并测试服务，确认工具安全分类中至少存在只读工具；不需要逐项勾选授权。
3. 在“群监听回复”新建监听器，选择群、引擎（MCP 或 Dify）和发送方式，按需调整轮次/调用预算。
4. 先使用“审核后发送”观察时间线和回答质量，再决定是否启用自动发送。
5. 检索异常时先导出单个工作项诊断；只有确需完整参数和结果时才临时开启详细日志。

高轮次并不等于更高质量。建议先通过工具描述和系统提示词改善查询路径，再提高轮次；轮次、调用量、模型费用和总耗时会同时增长，而且 MCP 总超时仍可能先终止任务。

## 开发与发布约束

开发机只运行 Python、前端和 Rust 源码级检查，以及 Vite renderer / Electron bundle 构建。禁止在本机运行 PyInstaller、EXE/NSIS 安装包构建或安装包自检。

Windows sidecar、安装包、签名和安装级冒烟验证只在 GitHub Actions Windows Runner 执行。正式版本以 `package.json` 为版本单源，提交到 `main` 后推送匹配的 `vX.Y.Z` 标签；不要修改或依赖 `src-tauri/**` 中的旧版本元数据。
